Дотримуйся правил нижче:

## 1. База

1.1. Основні архітектурні підходи: Clean Architecture і MVVM.
1.2. Якщо можна використати якісь патерни і вони доречні - використовуй
1.3. Давай прості і репрезентативні назви. Наприклад, extract() -> extractJsonFragment().
1.5. Не допускай `god object`. Максимум 400-500 рядків коду на файл.
1.6. Спільні UI-блоки винось у components/sections/files.
1.7. Мені НЕ потрібні безпечні міграції і тд, оскільки я роблю проєкт для себе.
1.8. В domain має бути чиста бізнес логіка, контракти і сутності. 
Суворо заборонено використання android специфічних класів і класів із data і ui
1.9. Має бути поділ на доменні і дата сутності.
Якщо сутність виходить за межі data layer додавай domain model.
Якщо вона потрібна тільки для Room/cache/sync — залишай тільки Entity.
В шарі data роби мапери у пакеті mappers із маперами для їх перетворення.
1.10. Дотримуйся принципу інверсії залежностей. Не роби одноразові файли. Краще - інтерфейси, зручні для розширення.
1.11. UseCases мають відображати дію з точки зору користувача, а не технічні сервіси. 
Вони повинні збирають кілька сервісів, операцій до купи. 
Тобто наприклад замість вузького технічного SendAIRequesUseCase -> AskAiUseCase

## 2. Хардкод

2.1. UI текст завжди винось у `app/src/main/res/values/strings.xml` і `app/src/main/res/values-en/strings.xml`.
2.2. Дати і час показуй через поточну локаль застосунку: `Locale.getDefault()`.
2.3. Числа і інші константні дані винось у const val CONSTANT_NAME.
2.4. Жоден текст не може бути захардкодений або написаний тільки з урахуванням однієї мови.

## 3. Help-Mode

3.1. Кожен ui елемент має підтримувати help-mode. Це режим, який відкривається через кнопку (?) справа зверху. При ньому основні блоки затемнюються і стають клікабельними. При натисненні з'являється пояснення.
3.2. Не накривай одну велику область, якщо секція складається з кількох окремих блоків: кожен логічний блок має відкриватися окремо.
3.3. Help-тексти завжди додавай у `values/strings.xml` і `values-en/strings.xml`. Формат: короткий маркерований список з `—`. Кожен пункт конкретний і чіткий.

## 4. Анімації

4.1. Не пиши локальні одноразові анімації, якщо вже є shared motion helpers.
4.2. Між головними екранами `Summary / Feed / Sources / Settings` анімацій не має бути взагалі. Для вкладених екранів, dialog, modal, … використовуй shared content/modal/visibility transitions.

## 5. Firebase Sync

5.1. Можливість синхронізації доступна для: джерел, підписок, збережених, налаштувань (крім API ключів), API-ключів.
5.2. Якщо нова модифікує щось із згаданого вище, то має пройти повний цикл синхронізації.
5.3. Потрібно оновити: локальне збереження, Firebase sync, mapper-и, DTO, backup/export/import, restore після входу на іншому пристрої, а також сумісність із уже існуючими даними.

## 6. Перевірка збірки
6.1. Після модифікацій запусти збірку командою ./gradlew assembleDebug із лімітом по часу 10 хвилин.
6.2. Виключення дрібні зміни, наприклад змінити якусь константу, додати логи, виправити іконку

## 7. Планування

7.1. Перед будь-якими модифікаціями короткий план реалізації. В першу чергу, щоб я зрозумів зміни.
7.2. Після цього не починай реалізацію. Я маю написати "OK" для погодження.
