# Agents.md

Твоє завдання — писати чистий, простий і продуктивний код, який легко підтримувати.

## 1. Архітектура і чистота коду

* Дотримуйся Clean Architecture і MVVM.
* `domain` — бізнес-логіка, контракти, use cases і domain models (entities). Без Android-класів, UI та залежностей від `data`.
* **Принцип «Один файл — одна сутність»**:
    * Кожна сутність (entity), модель (model), енум (enum) та мапер мають бути в окремому файлі.
    * Заборонено створювати файли-контейнери (наприклад, `Models.kt`, `CommonEnums.kt` або `Mappers.kt`).
    * Використовуй пакети для логічного групування за функціоналом (наприклад, `domain/entities/article/`, `data/mappers/source/`).
* `data` — DTO, data models, repository implementations, джерела даних і mapper-и.
* Якщо data model виходить за межі `data`, створи domain model і mapper у `mappers`.
* Дотримуйся Dependency Inversion: високорівневий код працює через інтерфейси, а не напряму з реалізаціями. Наприклад, use case залежить від `ArticleRepository`, а не від `FirebaseArticleRepository`.
* Дотримуйся Open-Closed: додавай нову поведінку через нові реалізації, не ламаючи існуючий код. Наприклад, нове джерело статей додається як ще одна реалізація `ArticleRepository`.
* UseCase має описувати дію користувача, а не технічний сервіс: `AskAiUseCase`, а не `SendAIRequestUseCase`.
* Назви мають бути прості й точні: `extractJsonFragment()` замість `extract()`.
* Уникай `god object`. Орієнтир: до 400–500 рядків на файл.
* Безпечні міграції не потрібні, якщо задача цього прямо не вимагає.

## 2. Хардкод і дублювання

* UI-тексти винось у `values/strings.xml` і `values-en/strings.xml`.
* Дати й час форматуй через `Locale.getDefault()`.
* Константи винось у `const val`.
* Не хардкодь текст і не пиши UI тільки під одну мову.
* Спільні UI-блоки винось у `components`, `sections` або окремі файли.

## 3. Help Mode

* Кожен важливий UI-елемент має підтримувати Help Mode.
* Help Mode відкривається через кнопку `?` справа зверху.
* У Help Mode логічні блоки затемнюються, стають клікабельними й показують пояснення.
* Якщо секція має кілька логічних блоків, кожен блок має окреме пояснення.
* Help-тексти додавай у `values/strings.xml` і `values-en/strings.xml`.
* Формат help-тексту: короткий список із `—`, кожен пункт конкретний.

## 4. Анімації

* Не створюй одноразові локальні анімації, якщо вже є shared motion helpers.
* Між головними екранами `Summary`, `Feed`, `Sources`, `Settings` анімацій не має бути.
* Для вкладених екранів, dialog і modal використовуй shared transitions.

## 5. Firebase Sync

Синхронізація стосується джерел, підписок, збережених, налаштувань і API-ключів.

Якщо зміна зачіпає ці дані, онови повний цикл: local storage, Firebase sync, mapper-и, DTO, backup/export/import, restore на іншому пристрої та сумісність з існуючими даними.

## 6. Перевірка збірки

* Після змін запускай `./gradlew assembleDebug` з лімітом 10 хвилин.
* Винятки: дрібні зміни на кшталт константи, логів або іконки.

## 7. Планування

* Перед модифікаціями дай короткий план.
* Не починай реалізацію без мого підтвердження.
* Починай тільки після мого `OK`.
